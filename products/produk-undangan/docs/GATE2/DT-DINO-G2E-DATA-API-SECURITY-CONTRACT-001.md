## Contract principles
- Organizer API uses verified authentication and event-scoped authorization on EVERY mutation and read.
- Guest routes expose only public event revision and an opaque invitation token; do not expose guest list, organizer private data or RSVP aggregation.
- Token generated by cryptographic randomness, transmitted securely and stored as hash; not in third-party analytics/referrers. Prevent URL token leakage through Referrer-Policy, cache controls and route design.
- RSVP endpoint accepts bounded fields and an idempotency key; rate limit, validate and prevent enumeration. Never trust event_id from guest without token authorization.
- Publish creates immutable revision and atomic pointer update; rollback points to prior valid revision with audit trail, not destructive overwrite.
- Guest personal data and asset retention are independent of hosted-access expiry. Scheduled deletion and backup expiry policies require approval.
- All monetary amounts represented as integer minor units with currency and provider settlement metadata. Do not process card details directly.

## Proposed API shape (not fixed)
POST /api/organizer/events; PATCH /api/organizer/events/:id/draft; POST /api/organizer/events/:id/publish; GET /api/organizer/events/:id/rsvps; POST /api/organizer/events/:id/rsvp-close; POST /api/organizer/events/:id/export; POST /api/organizer/events/:id/expire.
GET /i/:opaque_public_slug; POST /api/guest/rsvp with secure invitation proof.
The distinction between public event URL and private guest token must be resolved before implementation; no personal guest names in public URL.
